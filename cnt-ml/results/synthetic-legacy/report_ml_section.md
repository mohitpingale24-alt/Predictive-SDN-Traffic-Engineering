# Machine Learning Component: Short-Horizon Link Utilization Forecasting

## 1. Objective

The ML component forecasts link utilization five seconds into the future from recent per-link telemetry. The prediction can support proactive routing decisions when predicted utilization approaches the project's 85% congestion threshold.

## 2. Data Collection and Preprocessing

Phase A generated deterministic synthetic telemetry at one-second intervals for two links, `S1-S2` and `S1-S3`. Each link contains 3,600 seconds of data, for 7,200 raw rows in total. The revised generator includes multiple periodicities, bounded random walks, abrupt starts/stops, nonlinear burst decay, and sustained competing-flow periods distributed across the complete experiment. The current dataset contains 611 observations at or above 85% utilization.

Phase B removed duplicate `(timestamp, link_id)` rows, sorted records per link, clipped bounded measurements to valid ranges, and ensured that no missing values remained. Real sampling gaps are preserved and reported rather than silently interpolated. The current results remain from the earlier synthetic-data run and must not be used as real-network evidence.

## 3. Target Construction

For each link, the target at time $t$ is utilization at the exact timestamp $t+5$ seconds. Targets are joined by timestamp, never by row offset, so a sampling gap cannot silently change the prediction horizon. `target_timestamp` also allows boundary-crossing rows to be purged.

## 4. Feature Engineering

The tabular models use 14 features:

| Category | Features |
| --- | --- |
| Current state | utilization, throughput, delay, packet_loss, active_flows |
| Lagged utilization | util_lag_1, util_lag_2, util_lag_3, util_lag_5, util_lag_10 |
| Trend | util_ma_5s, util_ma_10s, util_slope |

The planned GRU representation uses raw per-timestamp telemetry over a ten-timestamp window, without the engineered lag and moving-average columns.

## 5. Train/Validation/Test Split

The data was split chronologically with no shuffling. Complete timestamps were kept together across links. Rows whose future label crossed from train into validation or validation into test were purged: ten rows at each boundary across the two links. The verified split sizes are 5,008 training rows, 1,066 validation rows, and 1,076 test rows.

## 6. Models Evaluated

- **Persistence:** predicts future utilization as the current utilization.
- **Linear Regression:** tests whether a simple linear model benefits from the engineered features.
- **Gradient Boosting:** six configurations tuned using validation RMSE only, with one final test evaluation.
- **GRU:** a ten-observation sequence model trained with early stopping and evaluated on the same held-out test rows.

The explicit development runtime is predictive control with Persistence. The
candidate production models are Gradient Boosting Regressor for congestion
decision quality, GRU for forecasting quality, and Linear Regression as the
lightweight baseline. No production model is permanently selected.

## 7. Evaluation Metrics

Models were evaluated using mean absolute error (MAE), root mean squared error (RMSE), R², and per-sample inference time. Accuracy and inference cost are both relevant because predictions may be called inside a live controller loop.

## 8. Results

Values below are from `results/metrics_comparison.csv` generated by the current synthetic-data run.

| Model | MAE (%) | RMSE (%) | R² | Inference time (ms) |
| --- | ---: | ---: | ---: | ---: |
| Persistence | **4.2537** | 8.7942 | 0.8815 | approximately 0 |
| Linear Regression | 4.8446 | 8.5507 | 0.8880 | 0.0003 |
| Gradient Boosting | 4.7443 | 8.6836 | 0.8844 | 0.0026 |
| GRU | 4.6052 | **8.4592** | **0.8903** | 21.7158 |

Persistence has the lowest MAE. GRU has the lowest RMSE and highest R², but its advantage over Linear Regression is small and its measured inference cost is much higher. Native XGBoost could not load in the verified macOS environment because `libomp.dylib` was unavailable, so the tested result is the scikit-learn Gradient Boosting fallback.

The test split contains 70 future-congestion samples. At the 85% decision threshold, Gradient Boosting Regressor has the best F1 (0.8130) and precision (0.9434), while GRU has the best recall (0.7571). Persistence remains the safe development default until the comparison is repeated on real telemetry.

## 10. Discussion

No single model is best on every criterion. The operational choice depends on whether unnecessary reroutes or missed congestion are more costly. Real Mininet/Ryu telemetry with controlled high-load events is required before changing the deployed model.

The Linux harness compares static routing, reactive control, predictive
Persistence, and predictive Gradient Boosting Regressor using an identical
iperf3 workload. It records latency, throughput, loss, jitter, congestion
duration, reroutes, inference time, controller CPU, Congestion Avoidance Rate,
and False Reroute Rate. Alternative-path utilization is projected after moving
the active load so an idle path's zero reading cannot cause premature recovery.

## 11. Limitations

- The dataset is synthetic and may not represent real controller, switch, queue, or traffic behavior.
- The test set has 70 threshold events, but all are synthetic.
- The experiment covers one hour and two links only.
- Overall prediction metrics do not prove that routing decisions reduce congestion, delay, packet loss, or flow completion time.
- OpenFlow port statistics do not expose link delay or instantaneous queue occupancy; the live exporter uses explicit zero placeholders for those fields.
- Live Mininet/Ryu execution and end-to-end network improvement have not yet been verified on this Mac.
- The selected model should be re-evaluated after real telemetry is collected and the B-H pipeline is rerun.
